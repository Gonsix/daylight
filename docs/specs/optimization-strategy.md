# 最適化方針

Daylightは、Vault内のノートを正本として外部編集・同期・リネームを反映しながら、表示に無関係な処理を減らす。以下は現在の実装であり、処理時間の目標値や特定のノート数での性能を保証するものではない。

## 1. 対象フォルダから探索する

起動時のメタデータ確認とアイテム一覧の作成は、設定されたルートの `Tasks`、`Events`、`Projects` を直接取得し、それぞれの子フォルダを再帰的にたどる。Vault全体のMarkdown一覧からの絞り込みは行わない。存在しないフォルダは空として扱う。保存先を移動した後は設定済みの新しいルートを使う。

当日分を判定するには各ノートのメタデータが必要なため、初期構築では対象フォルダの当日以外のノートも調べる。繰り越し、日またぎ、プロジェクト、親子関係の情報も必要であり、ファイル名だけで当日分を選別しない。

## 2. ノート単位でキャッシュする

構築済みアイテムをパス単位で保持する。外部から対象ファイルが更新・作成・削除・改名された場合は該当するパスを無効化し、次の一覧構築で変更されたものを再解析する。Daylightと無関係なファイルの通常の変更では一覧の無効化を行わない。フォルダの変更や、明示的に全体を無効化する一部の操作では全体を再構築する。

リンク解決は他のファイルにも依存するため、Obsidianの `resolved` イベント時にはキャッシュ済みアイテムのプロジェクト・親タスクの解決先を確認し、変わったものだけ再構築する。この確認自体はキャッシュ済みアイテム数に応じた処理を伴う。更新通知は約16msの間まとめる。保存直後のメタデータ遅延に対する一時的な状態・順序・実績の上書きは引き続き使用する。

## 3. 画面集計を必要なときに行う

月カレンダーの日別件数は、カレンダーを開いているときだけ算出する。開いている間は対象の42日について集計し、月やアイテムが変わったときに再計算する。プロジェクト別のタスク件数は、アイテムを一度走査してまとめて計算し、アイテムが変わるまで結果を再利用する。

## 4. タイムラインの時刻更新を絞る

選択日または対象アイテムが変わったとき、その日に重なる可能性のある予定・実績を候補として保持する。日またぎの予定と、選択日より前から継続中の実績も候補に含める。30秒ごとの時刻更新では、この候補だけから枠を再計算する。候補に実行中セッションがなければ枠の再計算は行わず、現在時刻の線は更新する。

候補抽出自体は日付・アイテムが変わると対象を走査する。日付別索引や永続キャッシュは現在実装していない。大量データで必要になった場合は、実測を基に追加を検討する。

## 検証と今後の測定

対象フォルダの再帰探索、対象外の変更、対象ノートとリンク先の更新、カレンダーを閉じた状態、日またぎと実行中のタイムラインについて自動テストを設ける。仕様の正しさと性能は別に評価する。実Vaultで起動時・ファイル変更時・日付切り替え時の処理時間と表示までの時間を測り、ノート数やセッション数を増やした場合の変化も確認する。今回の自動テストは実際のObsidian起動速度を測定するものではない。
